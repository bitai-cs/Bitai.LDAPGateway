## Step 4: Design rules and pitfalls

1. **Staleness model.** The backplane is at-most-once. A missed notification is bounded by `MemoryCacheDuration`, unless the reconciler catches the loss through the generation (reconnect, gap). Choose `MemoryCacheDuration` per data class and write the bound down. Do not describe the TTL as a guarantee for tags until Step 5 verified it for the version in use. The bound holds with fail-safe **disabled**. If fail-safe is enabled, an expired entry can still be served when a factory or L2 call fails, so the worst-case stale-serving window is the longest of: the L1 duration, the fail-safe maximum duration, and any other stale fallback configured. State that window per data class, not just `MemoryCacheDuration`.
2. **Reconnect flush and reconciliation.** **MUST** (option A): every process handles `IConnectionMultiplexer.ConnectionRestored`, malformed generation events, and generation gaps by marking itself dirty and flushing its **own** L1 with the local-only `ClearAsync` (Step 3e). Never use the default `ClearAsync()`/`RemoveByTagAsync` for the repair; they propagate to every node.
3. **Prefer tags for fan-out invalidation**, but every entry that must be reachable has to be written with that tag, tag invalidation is logical (payloads stay until TTL), and tags should not be over-used. A list query must carry every tag of the entities it contains, or a tag that every mutation of those entities also invalidates (Step 2).
4. **No invalidation loops.** Nothing in the reconciler republishes or removes anything cluster-wide; it only clears locally.
5. **Invalidate after commit** (outbox/cascading message), never inside the transaction, and understand the conditions that make it real (Step 3f).
6. **Shared Redis across environments or services:** isolate with `KeyPrefix`, a distinct `ChannelPrefix` (which also scopes the generation key and channel), per service and environment, otherwise unrelated services invalidate each other or mask each other's gaps. **Serialization and rolling deploys:** old and new pods share L2. Version the `KeyPrefix` (`v2:`) when the cached type changes incompatibly.
7. **In-flight factory race (not solved by invalidation or by the backplane).** A reader may start a factory, read the old row, and finish *after* the commit and the invalidation, writing the stale value back to L1/L2. Options: **(a)** put a row version in the key or in the cached DTO and validate it on read; **(b)** use short durations for data that cannot tolerate this window; **(c)** accept the window and document it per data class. Do not claim the design is free of this race.
8. **Stampede protection is per node, and a miss is announced.** FusionCache coalesces concurrent misses on a node; N pods can still each hit the database once on a cold key (and all of them do after a flush). A factory run also sends a backplane notification, so a node that refills a key makes the other nodes drop their L1 copy of it and reload from L2; after a flush this can ripple across the cluster [Assumption: derived from the documented notification behavior; measure it in the load test]. For very expensive factories, warm the key from a Wolverine handler or use a distributed locker (FusionCache offers one; confirm the package for the version in use) and fall back to running the factory if the lock cannot be acquired, because a lock may expire or Redis may fail mid-factory.
9. **Do not cache inside repositories that are used in write paths** (risk of read-your-own-stale-write). Cache in query handlers / read-side services.
10. **Observability:** log published/received invalidations at Debug with counts, never raw keys/tags (tenant identifiers, log cardinality). Emit the Step 3e metrics, register the meter in OpenTelemetry, enable FusionCache's logging/OpenTelemetry for hits, misses, fail-safe activations, and backplane errors, and track hit ratio per key prefix. Alert on `cache_reconcile_flushes` rate, `cache_generation_malformed`, and `cache_reconciler_ready == 0`.
11. **Redis down:** FusionCache can fall back to the factory (or to a stale value with fail-safe) when L2 or the backplane is unavailable. Ensure `AbortOnConnectFail=false`, bounded `ConnectTimeout`/`SyncTimeout`/`AsyncTimeout` (see `CachingOptions`), and that invalidation retries (Step 3f) do not block business handlers (they run on their own queue). Decide per data class whether fail-safe (serving an expired value on error) is acceptable; it is a staleness policy, not only a resilience feature. The multiplexer is a singleton, so `Connect` runs once; never create a connection per request.
12. **Security:** TLS and authentication for Redis outside dev; no PII in keys or tags (they appear in Redis and in logs). Use a Redis ACL user for the service with the minimum permissions: `SUBSCRIBE`/`PUBLISH` on the FusionCache backplane channel (its name is built from `ChannelPrefix` plus a protocol-version suffix, for example `orders:prod.Backplane:v2` in the scratch run; check it with `PUBSUB CHANNELS` on the version in use) and on `GenerationChannel`, `INCR`/`GET` on `GenerationKey`, and the key patterns/commands the L2 cache needs under `KeyPrefix`. Keep credentials in a secret store, not in `appsettings.json`.
