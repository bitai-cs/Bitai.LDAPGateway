# C# / .NET Specialist

Produce clean, well-designed, secure, fast, readable and maintainable C# that follows .NET conventions. Release notes for the current versions: https://learn.microsoft.com/en-us/dotnet/core/whats-new and https://learn.microsoft.com/en-us/dotnet/csharp/whats-new.

Follow the project's own conventions first, then common C# conventions. If the project's architecture or another skill (for example `wolverinefx` or a Clean Architecture agent) requires abstractions such as repositories, that takes precedence over the "no extra interfaces" rule below.

For tests, read `references/testing.md` before writing or reviewing them.

## Before changing code

- Read the target framework (TFM) and C# version, and check `global.json` for the SDK.
- Identify the app type (web, desktop, console, library), the packages (and multi-targeting), whether nullable is enabled (`<Nullable>enable</Nullable>` or `#nullable enable`), and repo config such as `Directory.Build.*` and `Directory.Packages.props`.
- Do not set a C# version newer than the TFM default, and do not change the TFM, SDK or `<LangVersion>` unless asked.
- C# 14 (.NET 10+): extension members, the `field` accessor, implicit `Span<T>` conversions, `?.=`, `nameof` with unbound generics, lambda parameter modifiers without types, partial constructors and events, user-defined compound assignment.
- Prefer modern C# (file-scoped namespaces, raw `"""` strings, switch expressions, ranges and indices, async streams) when the TFM allows.
- If syntax is unfamiliar, compile or check the docs first. Do not "correct" syntax that compiles.

## Build

- .NET 5+: `dotnet build` and `dotnet publish`.
- .NET Framework: `MSBuild` directly, or Visual Studio may be required.
- Look for custom targets and scripts first: `Directory.Build.targets`, `build.cmd`/`build.sh`, `Build.ps1`.

## Code design rules

- Do not add interfaces or abstractions unless they serve an external dependency or testing. Do not wrap existing abstractions.
- Least exposure: `private` > `internal` > `protected` > `public`. Do not default to `public`.
- Keep naming consistent: pick one style and stick to it.
- Do not edit generated code (`*.g.cs`, files marked `// <auto-generated>`).
- Comments explain why, not what. Add a doc comment when adding a public method.
- Do not add unused methods or parameters. Reuse existing methods as much as possible.
- When fixing one method, check its siblings for the same issue.
- Keep diffs small and avoid new layers unless needed. Keep code IDE-friendly (go-to-definition, rename and quick fixes keep working).
- Move user-facing strings into resource files; keep error and help text localizable.
- Prefer records over classes for DTOs.

## Error handling

- Null checks: `ArgumentNullException.ThrowIfNull(x)`; `string.IsNullOrWhiteSpace(x)` for strings; guard early; avoid blanket `!`.
- Throw precise exception types (`ArgumentException`, `InvalidOperationException`, ...). Do not throw or catch the base `Exception`.
- No silent catches: log and rethrow, or let the exception bubble. Keep cause and context.

## Production readiness

- Security: no secrets in code, validate input, least privilege; consider authentication, authorization and data protection.
- Resilience: timeouts on I/O, retry with backoff where it fits.
- Logging: structured, with scopes and useful context; no log spam.
- Performance: simple first, optimize measured hot paths. Stream large payloads, avoid extra allocations, use `Span`/`Memory`/pooling when it matters.
- Cloud-ready: cross-platform (guard OS-specific APIs), health and readiness endpoints when they fit, metrics and traces, `ILogger` plus OpenTelemetry hooks, 12-factor configuration from the environment, no stateful singletons.

## Async

- All async methods end with `Async`.
- Always await. No fire-and-forget; if a call times out, cancel the work.
- Accept a `CancellationToken` and pass it through end to end. Call `ThrowIfCancellationRequested()` in loops and make delays cancelable (`Task.Delay(ms, ct)`).
- Timeouts: a linked `CancellationTokenSource` with `CancelAfter`, or `WhenAny` and then cancel the pending task.
- `ConfigureAwait(false)` in helper and library code; omit it in app entry points and UI.
- No sync-over-async.
- Large JSON: `GetAsync(..., ResponseHeadersRead)`, then `ReadAsStreamAsync`, then `JsonDocument.ParseAsync`; avoid `ReadAsStringAsync`.
- `ValueTask` only when measured to help; default to `Task`.
- Prefer `await using` for async disposables, with clear ownership of streams and readers.
- Do not add `async`/`await` when you only return the task.
- Console apps should return a non-zero exit code when cancelled (for example `130`).
