In 5 attempts to lose a message by killing the Pub/Sub connections right before the publish, none left a stale value, so that experiment is **inconclusive** (StackExchange.Redis resubscribes within milliseconds); the lost-message behavior rests on the simulation and on the documentation.
- This skill's code (2 hosts): key and tag invalidation through `ICacheInvalidator` reach the other node; a generation increment with no publish (publisher crash after `INCR`) is detected by the reconciler and the stale entry is no longer served within `2 x ReconcileInterval` (checked with `ReconcileInterval=2s`).
- Review fixes (2026-11-23), compiled and run in a second scratch project (same SDK and FusionCache 2.10.0, real Redis 8 on 127.0.0.1, `IFusionCache` replaced by an NSubstitute double where a flush had to be blocked): `CacheKeys.Key(null)` throws `ArgumentNullException`; a `null` factory result **is cached by default** and the adaptive `ctx.Options.Duration`/`DistributedCacheDuration` override applies to it (factory ran once for two reads, still cached inside the not-found duration, refreshed after it); the health check reports `Degraded` while `FlushAsync` is blocked and `Healthy` afterwards; if `ReadGenerationAsync` throws once after a successful subscribe, the loop retries and `HasSubscribed` becomes true; `StopAsync(ct)` returns promptly. **Negative control:** against the previous code the health check stays `Healthy` during the flush and `HasSubscribed` never becomes true, so those two tests do detect the defects.
- Same run, second batch (project `verification/`, 31 checks, all passing): partial failure after `INCR` injected at four points (first key removal, second key removal, tag removal, generation publish): the exception surfaces, the counter advances with no generation event, a second node's reconciler (`ReconcileInterval=1s`) confirms the gap and flushes, and a retry succeeds and publishes. The not-found duration also holds with a **real L2** (a miss cached by node A is served to node B without re-running the factory, and the new row appears after the duration). The tests use real Redis for the counter, channel and L2, and an NSubstitute double for `IFusionCache`, so the FusionCache removals themselves are simulated in the failure scenarios.
- **Wolverine snippets, re-run on 2026-11-23** (project `verification-wolverine/`; `WolverineFx` + `.EntityFrameworkCore` + `.SqlServer` + `.RuntimeCompilation` **6.65.1**, EF Core 10.0.15, SQL Server 2022 in a disposable container, 14 checks, all passing): the Step 2 command handler, the Step 3f configuration block and handler, and the `IDbContextOutbox<T>` endpoint compile and start. The invalidation runs after commit and sees the committed row (read with `READ COMMITTED` and a lock timeout, so an uncommitted write would have blocked); a handler that throws releases nothing; a `SaveChanges` failure (unique-index violation) **after** the handler returned the message releases nothing and leaves the row untouched; the endpoint path commits data and message together; a `RedisConnectionException` is retried by the `OnException` policy (one failure, two attempts). A child process killed with `Environment.FailFast` inside the invalidation handler, after the commit, left the envelope in the database and a restarted host delivered it after **66-81 s** (three runs; the stale node is ejected after missed health checks, as before). Findings: the Step 3f snippet needs `using Wolverine.ErrorHandling;` (and `JasperFx.Core` for `50.Milliseconds()`), otherwise `OnException` does not compile; the plain `AddDbContext<T>` registration was enough for the transactional middleware and for `IDbContextOutbox<T>` on SQL Server (the `AddDbContextWithWolverineIntegration` variant was not run there).
